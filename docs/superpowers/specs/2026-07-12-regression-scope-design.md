# regression-scope: подбор тест-кейсов для регресса по задаче

Дата: 2026-07-12
Статус: дизайн утверждён

## Задача

QA получает задачу разработки в Redmine и должен собрать регрессионный набор: тест-кейсы на **существующую** функциональность, которую задевает изменение. Скилл автоматизирует цикл: изучить задачу и ТЗ → найти затронутые области → отобрать релевантные кейсы в Allure TestOps → оформить тест-план.

## Архитектура

Один скилл `skills/regression-scope/SKILL.md` с двумя типами делегирования:

1. **Сбор требования** — существующий агент `agents/doc-researcher.md` (read-only, изолированный контекст). Возвращает выжимку: что меняется, какие фичи/модули задеты, неоднозначности.
2. **Оценка кандидатов** — generic суб-агенты пачками по 20–30 кейсов. Алгоритм и критерии передаются **явно в промпте** (суб-агент SKILL.md не читает — проверено на review-autotest).

Отдельный именованный агент для оценки не создаётся: второго потребителя нет (YAGNI).

## Входные данные

- Номер задачи Redmine («подбери регресс по задаче 123») — обязателен.
- Целевой проект Allure: по умолчанию 35 (тестовый), другой — только если пользователь указал явно.

## Источники ТЗ (все возможны, проверять по порядку)

1. Описание задачи Redmine + комментарии (`redmine_request`, `include=journals,attachments,relations`).
2. Вложения задачи (docx/pdf) — скачать, распарсить (скиллы anthropic-skills:docx / anthropic-skills:pdf).
3. Связанные/родительские задачи Redmine.
4. Документ Kaiten — по ссылке из задачи или поиском (`kaiten_list_documents` → `kaiten_get_document`); ТЗ может быть текстом документа или вложенным файлом.

ТЗ не найдено нигде → остановиться и спросить пользователя. Поведение системы не выдумывать.

## Разметка кейсов в Allure (подтверждено анализом проекта 35)

Кастомные поля `Section1`–`Section5` — уровни дерева фич (пример: Section1 «🚀 Demo» → Section2 «Импорт/Экспорт» → Section3 «Импорт/Экспорт проекта через JSON»). Поле «Приоритет» — required, single-select. Значения полей и `testCasesCount` доступны через `list_custom_field_values` — дёшево, без выкачивания кейсов.

## Алгоритм

1. **Выжимка ТЗ**: делегировать `doc-researcher` (источники выше). Неоднозначности показать пользователю до отбора.
2. **Карта секций**: `list_project_custom_fields` + `list_custom_field_values` по Section1–Section5.
3. **Матчинг**: сопоставить затронутые фичи из выжимки со значениями секций. Затронутые секции → `search_test_cases` с RQL `cf["SectionN"] = "<значение>"` → список кандидатов (ID + название).
   - Секции не сматчились → fallback: `name ~ "<ключевые слова>"`; результаты пометить как спорные.
4. **Оценка кандидатов**: суб-агенты пачками 20–30 ID. Каждый получает: выжимку ТЗ, список ID, алгоритм оценки, правила чтения сценария (`get_test_case_scenario` / `get_test_case_steps`; shared steps резолвить через `get_shared_step_steps` по `sharedStepId`; ОР шага может отсутствовать — fallback на `overview.expectedResult`). Возвращает по каждому кейсу: **взять / не брать / спорно** + причина одной строкой.
5. **Таблица пользователю**: ID (ссылкой `https://astbroker.qatools.cloud/project/<proj>/test-cases/<id>`), название, Приоритет, вердикт, причина. Спорные — отдельным блоком, решает пользователь.
6. **После подтверждения**: `create_test_plan` с выбранными кейсами. Название плана: «Регресс: <тема задачи> (redmine-<id>)». Отчитаться ссылкой на план.

## Краевые случаи

- Релевантных кейсов нет → честно сказать: регресс по задаче не требуется либо покрытие отсутствует (предложить скилл test-design).
- Кандидатов слишком много (>150) → предупредить пользователя, предложить сузить секции до запуска суб-агентов.
- `create_test_plan` запрещён deny-масками (read-only режим) → сообщить и выдать итоговый список текстом.

## Ограничения

- Redmine и Kaiten — только чтение.
- В Allure запись только тест-плана и только после подтверждения пользователя.
- Кейсы не изменяются, теги не проставляются.

## Тестирование

E2E чек-лист (живое окружение):
1. Задача с ТЗ в описании → тест-план создан, кейсы релевантны.
2. Задача с ТЗ в Kaiten (документ) → ТЗ найдено по ссылке/поиску.
3. Задача с ТЗ вложением (docx/pdf) → файл скачан и разобран.
4. Задача без релевантных кейсов → пустой результат с честным ответом, план не создан.
