# Дизайн: скилл `review-autotest`

Дата: 2026-07-11
Статус: утверждён, готов к плану реализации

## Задача

Ревью автоматизированного теста: сопоставить требования Redmine-задачи, ручной тест-кейс в Allure TestOps и код автотеста (pytest + allure-pytest). Выдать структурированный отчёт с конкретными правками — в стиле существующего скилла `review-testcase`. Read-only: код и кейсы не меняем.

## Архитектурное решение

**Скилл-оркестратор**, а не агент-обёртка. Рабочий процесс линейный (источник → источник → сопоставление), параллельных веток нет — поэтому inline MCP-вызовы в главном треде. Делегация суб-агентам — точечная, только для контроля контекста в пачечном/многотестовом режиме (см. ниже). Паттерн повторяет уже работающий `review-testcase`.

Скилл запускается **из cwd репозитория автотестов** (отдельная git-репа, клонирована локально). Код автотестов находится grep-ом от текущей директории. Связка кейс ↔ код — через декоратор `@allure.id("<id>")` в коде.

## Режимы (определяются по входу)

| Вход | Режим | Объём |
|------|-------|-------|
| Redmine-задача (`#1234` / ссылка) | Пачка | Все связанные TestOps-кейсы задачи |
| TestOps-кейс (id / ссылка `.../test-cases/<id>`) | Одиночный | Один кейс + его автотест |
| GitLab MR (ссылка) | Diff-центричный | Только изменённые в MR тест-файлы |

### Одиночный режим (inline, без агента)

```
1. Allure MCP: get_test_case_overview + get_test_case_steps → ручной сценарий, метаданные
2. Если у кейса есть Redmine-ссылка → redmine_request → требования задачи
3. grep -r '@allure.id("<id>")' от cwd → файл автотеста
4. Read файла теста → код
5. Сопоставление по 4 измерениям → отчёт по блокам + вердикт
```

### Пачечный режим (Redmine-задача, делегация)

```
1. redmine_request → задача + список связанных TestOps-кейсов + требования (ОДИН раз в главном треде)
2. На каждый кейс → суб-агент general-purpose:
     вход: case_id + выжимка требований задачи + путь cwd репы
     агент сам: Allure MCP (кейс) + grep + Read (автотест) + ревью по 4 измерениям
     выход: СЖАТЫЙ вердикт по кейсу (блоки с замечаниями + статус)
3. Главный тред: сводная таблица (кейс → статус → кол-во замечаний) + детали по проблемным
```

Требования Redmine тянутся один раз в главном треде и передаются агентам выжимкой — агенты не дёргают Redmine повторно.

### MR-режим (diff-центричный)

```
1. Достать MR:
   - если ветка MR есть локально → git diff main...<branch> → изменённые тест-файлы
   - иначе → GitLab API (curl / glab) по URL → diff + описание MR (нужен read-only GitLab-токен)
2. Из описания MR извлечь номер Redmine-задачи → требования
3. Из изменённых тест-файлов извлечь @allure.id → соответствующие кейсы TestOps
4. Ревью каждого изменённого теста (при большом числе — делегация, как в пачке)
5. Вывод: сводка + детали (как в пачечном режиме)
```

MR-режим центрируется на diff — ревьюим только изменённые тесты, не всю репу.

## Измерения ревью (4 блока)

### Блок 1. Соответствие код ↔ ручной кейс
- Каждый шаг ручного сценария имеет отражение в коде (действие + проверка).
- Ожидаемый результат кейса = ассерт в коде. Нет проверки на заявленный ОР → замечание.
- Лишние проверки в коде, которых нет в кейсе, или наоборот (рассинхрон) → замечание с указанием, что синхронизировать.
- Предусловие кейса = fixture/setup. Не реализовано → замечание.

### Блок 2. Покрытие требований Redmine
- Ключевые требования задачи покрыты связкой кейс+тест. Непокрытое → «нет проверки на <требование>».
- Негативные/граничные сценарии из задачи — есть ли автотест.

### Блок 3. Качество кода pytest
- Ассерты: не пустые, не заглушки (`assert True`, `pass`, закомментированные), с сообщением.
- Антипаттерны: `time.sleep` (флейк), хардкод (урлы/логины/id вместо fixture/config/params), закомментированный код, `print` вместо логов.
- Структура: одна проверка = один тест (или обоснованная параметризация), нет дублей, осмысленные имена.
- Allure-шаги: `with allure.step(...)` покрывают логику, не один шаг на весь тест.

### Блок 4. Метаданные / связность
- `@allure.id("<id>")` на месте, ведёт на существующий кейс TestOps.
- `@allure.title` совпадает или осмысленно близок к названию кейса. Рассинхрон → замечание.
- Severity/теги проставлены, если требует стандарт.
- Кейс в TestOps не «протух» относительно кода (шаги ≈ код).

## Формат вывода

Наследует правила `review-testcase`: пустые блоки не включаются; если замечаний нет ни по одному блоку → одна строка «Автотест соответствует кейсу и требованиям, правки не требуются»; формулировки конкретные (что, где, как исправить), без «желательно/можно укоротить».

### Одиночный / один тест в MR — по блокам

```
Ревью автотеста: <название> (кейс 39979, test_calc_gap.py:42)

1. Соответствие кейсу
   - Шаг 3 «Выбрать риск ГАП» не отражён в коде — нет действия и проверки

   Правка:
   - Добавить allure.step + assert на выбор риска ГАП

3. Качество кода
   - test_calc_gap.py:51 — time.sleep(5), флейк-паттерн

   Правка:
   - Заменить на явное ожидание элемента (WebDriverWait / expect)

Вердикт: Нужна доработка
```

### Пачка / MR с несколькими тестами — сводка + детали

```
Ревью: задача #1234 — 5 кейсов

| Кейс  | Тест           | Статус          | Замечаний |
|-------|----------------|-----------------|-----------|
| 39979 | test_calc_gap  | Нужна доработка | 2         |
| 39980 | test_calc_base | Готов           | 0         |
| 39981 | — (не найден)  | ⚠ нет автотеста | —         |

Детали ниже — только по кейсам с замечаниями.
[блочные разборы проблемных]
```

## Краевые случаи

- **Автотест не найден** (`@allure.id` нет в репе) → замечание «нет автотеста на кейс», не падаем.
- **Кейс без Redmine-ссылки** → блок 2 пропускаем, помечаем «требования не проверены (нет связи с задачей)».
- **Ручной кейс пустой** (нет шагов) → блок 1 ограничен, отмечаем.
- **Allure / Redmine / GitLab API ошибка** → сообщаем пользователю, останавливаем (как review-testcase).
- **MR без изменённых тест-файлов** → сообщаем «в MR нет автотестов», стоп.
- **Один `@allure.id` в нескольких файлах** → замечание «дубль привязки».

## Зависимости

- Allure TestOps MCP (чтение кейсов, шагов, overview) — уже есть.
- Redmine MCP (`redmine_request`, чтение задач) — уже есть.
- GitLab-доступ: git локально (без токена) ИЛИ GitLab API через curl/`glab` (read-only токен, опционально; добавить в конфиг плагина).
- Bash / Grep / Read — инспекция кода в cwd.
- Агент `general-purpose` — точечная делегация в пачечном/MR-многотестовом режиме.

## Не входит в объём (YAGNI)

- Правка кода автотестов / кейсов (только read-only отчёт).
- Запуск/прогон тестов.
- Поддержка не-pytest стеков (Java/JS) — только pytest + allure-pytest.
- Автоматическая синхронизация кейса TestOps с кодом.
