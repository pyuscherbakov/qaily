# review-autotest Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Скилл `review-autotest` — ревью автотеста (pytest + allure-pytest) через сопоставление требований Redmine, ручного кейса Allure TestOps и кода автотеста; read-only отчёт в стиле `review-testcase`.

**Architecture:** Один прозаический файл `skills/review-autotest/SKILL.md` — инструкция-оркестратор. Три режима входа (Redmine-задача → пачка, TestOps-кейс → одиночный, GitLab MR → diff). Inline MCP-вызовы в главном треде; точечная делегация суб-агентам `general-purpose` для контроля контекста в пачечном/многотестовом режиме. Регистрация — авто-подхват из `skills/` (в plugin.json не прописывается). GitLab API-путь MR-режима требует опционального read-only GitLab-токена — добавляется в `userConfig`.

**Tech Stack:** Claude Code plugin skill (Markdown + frontmatter). MCP: allure-testops (чтение), redmine (`redmine_request`). Bash/Grep/Read для кода. Стек ревьюемых автотестов — Python pytest + allure-pytest, связка кейс↔код через `@allure.id("<id>")`.

## Global Constraints

- Скилл **read-only**: не меняет код автотестов и кейсы TestOps. Только отчёт.
- Всё общение и содержимое SKILL.md — на русском (единообразно с `review-testcase`, `test-design`).
- Наследуемые из `review-testcase` правила вывода: пустые блоки не включаются; нет замечаний ни по одному блоку → одна строка «Автотест соответствует кейсу и требованиям, правки не требуются»; формулировки конкретные (что / где / как исправить), без «желательно / можно укоротить / оптимизировать».
- Связка кейс↔код строго через декоратор `@allure.id("<id>")` — grep от cwd.
- Скилл запускается из cwd репозитория автотестов.
- Коммиты на русском, без `Co-Authored-By`.
- Файл SKILL.md держать < 500 строк (правило проекта); если растёт — не выносить в отдельные файлы без нужды, но следить за объёмом.
- Валидация каждой задачи — E2E-прогон скилла на реальных данных (нет юнит-тестов у прозаического скилла). Фикстуры: Allure проект 35 (`https://astbroker.qatools.cloud/project/35`), реальный кейс с `@allure.id` в репе автотестов; Redmine проект `pfpa`. Перед стартом исполнитель уточняет у пользователя конкретные ID кейса/задачи/MR для прогонов, если приведённые недоступны.

- [ ] **Step 1: Записать 4 блока критериев**

Заменить заглушку секцией (критерии — verbatim из спеки, файл `docs/superpowers/specs/2026-07-11-review-autotest-design.md`, раздел «Измерения ревью»):

```markdown
## Блоки ревью

### Блок 1. Соответствие код ↔ ручной кейс
- Каждый шаг ручного сценария имеет отражение в коде (действие + проверка).
- Ожидаемый результат кейса = ассерт в коде. Нет проверки на заявленный ОР → замечание.
- Лишние проверки в коде, которых нет в кейсе, или наоборот (рассинхрон) → замечание с указанием, что синхронизировать.
- Предусловие кейса = fixture/setup. Не реализовано → замечание.

### Блок 2. Покрытие требований Redmine
- Ключевые требования задачи покрыты связкой кейс+тест. Непокрытое → «нет проверки на <требование>».
- Негативные/граничные сценарии из задачи — есть ли автотест.

### Блок 3. Качество кода pytest
- Ассерты: не пустые, не заглушки (`assert True`, `pass`, закомментированные), с сообщением.
- Антипаттерны: `time.sleep` (флейк), хардкод (урлы/логины/id вместо fixture/config/params), закомментированный код, `print` вместо логов.
- Структура: одна проверка = один тест (или обоснованная параметризация), нет дублей, осмысленные имена.
- Allure-шаги: `with allure.step(...)` покрывают логику, не один шаг на весь тест.

### Блок 4. Метаданные / связность
- `@allure.id("<id>")` на месте, ведёт на существующий кейс TestOps.
- `@allure.title` совпадает или осмысленно близок к названию кейса. Рассинхрон → замечание.
- Severity/теги проставлены, если требует стандарт.
- Кейс в TestOps не «протух» относительно кода (шаги ≈ код).
```

## MR-режим (GitLab merge request, diff-центричный)

1. **Достать изменённые тест-файлы:**
   - если ветка MR есть локально → `git diff --name-only <base>...<branch>` (base по умолчанию `main`/`master` — определи по репе) → отфильтруй тест-файлы (`test_*.py` / `*_test.py`);
   - иначе → GitLab API по URL MR через `curl` (`GET /projects/:id/merge_requests/:iid/changes`, заголовок `PRIVATE-TOKEN: $GITLAB_TOKEN`) или `glab mr diff`, если установлен. Токен не задан → сообщи, что для удалённого MR нужен GitLab-токен, предложи вариант с локальной веткой.

5. **Вывод:** сводка + детали.
