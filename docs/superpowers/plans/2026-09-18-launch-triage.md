# Launch Triage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Скилл `launch-triage`: по ID упавшего запуска Allure TestOps выдать в чат сводку падений, сгруппированных по корневой причине, с контекстом Redmine-задачи запуска.

**Architecture:** Главный тред ходит только за статистикой запуска и сводит группы; всё тяжёлое чтение (результаты с `trace`, текст задачи с примечаниями) делает суб-агент `failure-analyst` в трёх режимах — `scan` (страница результатов → сигнатуры), `context` (Redmine-задача → выжимка), `drill` (группа → корневая причина). Стеки и тела задач в главный тред не попадают.

**Tech Stack:** Markdown-скилл Claude Code + суб-агент; MCP `testops` (официальный сервер ТестОпс, HTTP), MCP `redmine` (mcp-redmine).

**Spec:** отдельного spec-документа нет — дизайн согласован в чате и зафиксирован ниже в разделах «Проверенные факты» и «Алгоритм». План аргументирует от них.

## Global Constraints

- Скилл **read-only**: не создаёт и не меняет кейсы, дефекты, задачи, карточки Kaiten; файлов не пишет. Вывод — текст в чат.
- Kaiten в этом скилле не используется вообще.
- Типы причин — фиксированные пять: `инфра/авторизация`, `тестовые данные/окружение`, `дефект автотеста`, `продуктовый дефект`, `неясно/флак`.
- Имена MCP-инструментов — с префиксом плагина: `mcp__plugin_qaily_testops__*`, `mcp__plugin_qaily_redmine__redmine_request`.
- Файлы держать под 500 строк (правило проекта).
- Коммиты на русском, без `Co-Authored-By`.
- Лимиты параллелизма: до 8 агентов `scan`, до 12 агентов `drill` на один прогон.

## Алгоритм (что должен делать скилл)

1. Вход: launch ID (`5034`) или ссылка `https://astbroker.qatools.cloud/launch/5034`. `projectId` — параметр, дефолт из Task 4.
2. `testops_find_launches`, `aql: "id = <launch>"`, `expand: ["statistic","issues","release","category","defect","unresolved","uncategorized"]`.
3. Падений (`failed` + `broken`) ноль → «прогон зелёный», стоп. Запуск не найден → спросить `projectId`.
4. Номер Redmine-задачи: `issues[0]`, если строка из цифр; иначе `release`, если строка из цифр; иначе — без контекста (пометка в сводке).
5. Параллельно: агент `mode=context` (задача) и агенты `mode=scan` (страницы результатов по 50).
6. Мерж сигнатур из всех `scan`-ответов в главном треде; группы <2 падений → блок «прочее».
7. На каждую группу — агент `mode=drill` с выжимкой задачи.
8. Сводка в чат.

```markdown
## Режим `scan` — страница результатов → сигнатуры

**Вход:** `projectId`, `launch` (id запуска), `page` (0-based), `size` (обычно 50).

**Что делать:**
1. `testops_find_testresults` с `projectId`, `aql: "launch = <launch> and status in [\"failed\",\"broken\"]"`, `page`, `size`, `sort: ["id,ASC"]`. `expand` НЕ передавай — `message` и `trace` приходят и так.
2. Для каждого результата собери сигнатуру из первой строки `message` (нет `message` — из первой содержательной строки `trace`):
   - целые и дробные числа → `<N>`;
   - UUID и хэши (32+ hex) → `<UUID>`;
   - даты и время в любом виде → `<DATE>`;
   - id внутри URL и путей (`/contracts/8123/`) → `/<N>/`;
   - кавычки с конкретными значениями (`'ВЕСТА GFK350'`) оставляй — они несут смысл;
   - обрежь до 120 символов.
3. Схлопни результаты с одинаковой парой (`status`, сигнатура) в группу.

**Формат ответа:**

​```
### scan page <page>: прочитано <N> результатов, групп <M>
- SIG: <сигнатура> | <status> | N=<кол-во> | ids=<id1>,<id2>,<id3> | test=<имя одного теста>
- ...
```

Не больше 15 строк. Групп получилось больше — оставь топ-14 по количеству, последней строкой отдай `- SIG: <прочее> | mixed | N=<остаток> | ids=<до 3 id> | test=—`.
Страница пустая → одна строка `### scan page <page>: результатов нет`.
```

## Режим `drill` — группа падений → корневая причина

**Вход:** `projectId`, `signature`, `count`, `result_ids` (2–3 представителя), `issue_context` (выжимка из режима `context`; может быть пустой).

# Разбор упавшего прогона

Ты разбираешь упавший запуск Allure TestOps: берёшь статистику, находишь задачу запуска, раздаёшь чтение результатов суб-агенту `failure-analyst` и сводишь всё в одну сводку. Алгоритм чтения одного результата, правила нормализации сигнатур и типы причин живут в `agents/failure-analyst.md` — агент читает их сам, **не пересказывай их в промпте агента**.

## Вход

- Число (`4498`) или ссылка `https://astbroker.qatools.cloud/launch/<id>` → id запуска.
- `projectId` — по умолчанию <дефолт из Task 4>. Пользователь может задать явно.

## Критические правила

1. **Read-only.** Ни кейсы, ни дефекты, ни задачи не создаём и не меняем. Файлы не пишем — сводка идёт в чат.
2. **Делегирование обязательно.** Результаты прогона приходят вместе с `trace`; читать их в главном треде нельзя — контекст взорвётся. Любое чтение результатов и задачи — через `failure-analyst`.
3. **Задачу тянем один раз** — режимом `context`, и передаём выжимку всем `drill`-вызовам. Агенты Redmine сами не дёргают.
4. **Лимиты:** до 8 агентов `scan` параллельно, до 12 агентов `drill` на прогон.

## Краевые случаи

- **Запуск не найден** → спросить `projectId`, не перебирать проекты.
- **Падений нет** → «прогон зелёный», стоп.
