# regression-scope Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Скилл `regression-scope` — подбор тест-кейсов для регрессионного тестирования задачи: задача Redmine + ТЗ → затронутые секции Allure → оценка кандидатов суб-агентами → тест-план в TestOps.

**Architecture:** Один прозаический файл `skills/regression-scope/SKILL.md` — инструкция-оркестратор. Сбор требования делегируется существующему агенту `agents/doc-researcher.md` (расширяется: вложения Redmine, связанные задачи, режим «регресс»). Отбор кандидатов — инлайн через RQL по кастомным полям Section1–Section5. Оценка кандидатов — generic суб-агенты пачками 20–30 кейсов, алгоритм передаётся явно в промпте (суб-агент SKILL.md не читает). Регистрация скилла — авто-подхват из `skills/`.

**Tech Stack:** Claude Code plugin skill (Markdown + frontmatter). MCP: allure-testops (`list_project_custom_fields`, `list_custom_field_values`, `search_test_cases`, `get_test_case_overview`, `get_test_case_scenario`, `get_test_case_steps`, `get_shared_step_steps`, `create_test_plan`), redmine (`redmine_request`, `redmine_download`), kaiten (documents). Парсинг вложений: PDF — инструмент Read (читает нативно), DOCX — `textutil -convert txt` (macOS).

## Global Constraints

- Redmine и Kaiten — **только чтение** (скачивание вложений — тоже чтение).
- В Allure единственная запись — `create_test_plan`, и только после явного подтверждения пользователя. Кейсы не изменяются, теги не проставляются.
- Всё содержимое SKILL.md и общение — на русском (единообразно с `test-design`, `review-autotest`).
- Целевой проект Allure: 35 по умолчанию, другой — только если пользователь указал явно.
- Файлы держать < 500 строк.
- Коммиты на русском, без `Co-Authored-By`.
- Валидация — E2E-прогон на живом окружении (проект 35 `https://astbroker.qatools.cloud/project/35`, Redmine проект `pfpa`). Прозаический скилл, юнит-тестов нет. Перед прогонами исполнитель запрашивает у пользователя актуальные ID задач Redmine.
- Разметка кейсов (подтверждено анализом проекта 35): кастомные поля `Section1`–`Section5` = уровни дерева фич; поле «Приоритет» — required, single-select. RQL-синтаксис: `cf["Section2"] = "Импорт/Экспорт"`, `name ~ "подстрока"`, комбинаторы `and`/`or`/`not`.

```markdown
# Подбор регресса по задаче

Ты опытный QA-инженер, собирающий регрессионный набор. Регресс — кейсы на СУЩЕСТВУЮЩУЮ функциональность, которую задевает изменение из задачи; кейсы на новую функциональность задачи сюда не входят (для них есть скилл test-design).

## Входные данные

- Номер задачи Redmine («подбери регресс по задаче 123», ссылка `redmine.fast-system.ru/issues/123`) — обязателен. Нет номера — спроси.
- Целевой проект Allure: по умолчанию 35. Другой — только если пользователь указал явно.

## Критические правила

- Redmine и Kaiten — только чтение.
- Единственная запись в Allure — `create_test_plan`, строго после подтверждения пользователем итогового списка.
- Поведение системы не выдумывать: ТЗ не найдено или противоречиво → остановись и спроси пользователя.
- Формулировки причин конкретные: какой поток данных / какая функция задета, без «может быть связано».
```

```markdown
## Режимы
```

- [ ] **Step 1: Написать шаги 1–3 алгоритма**

Вместо заглушки:

```markdown
## Алгоритм

### Шаг 1. Выжимка ТЗ

Делегируй агенту `doc-researcher`: передай номер задачи Redmine, целевой проект Allure и строку «режим: регресс». Агент вернёт выжимку: Задача / Затронутые области / Неоднозначности / Источники ТЗ.

- Неоднозначности из выжимки покажи пользователю ДО отбора кейсов.
- В «Источниках ТЗ» значится, что ТЗ не найдено ни в задаче, ни во вложениях, ни в Kaiten → остановись и спроси пользователя, где ТЗ. Не выдумывай.

### Шаг 2. Карта секций Allure

Кейсы проекта размечены кастомными полями Section1–Section5 — это уровни дерева фич (Section1 — продукт/раздел, глубже — конкретные фичи).

1. `list_project_custom_fields` по проекту → id полей Section1–Section5.
2. Для каждого поля `list_custom_field_values` (у значений есть `testCasesCount` — пустые уровни пропускай).

### Шаг 3. Кандидаты

1. Сопоставь «Затронутые области» из выжимки со значениями секций (по смыслу, не только по точному совпадению строк).
2. Для каждой сматченной секции: `search_test_cases` с RQL `cf["SectionN"] = "<значение>"` (значение точно как в карте). Собери кандидатов: ID + название, без дублей.
3. Секции не сматчились или дали пусто → fallback: `search_test_cases` с `name ~ "<ключевое слово из области>"` по 2–4 ключевым словам; таких кандидатов сразу помечай как спорные.
4. Кандидатов больше 150 → покажи пользователю разбивку по секциям и предложи сузить выбор ДО запуска оценки.
5. Кандидатов нет вообще → сообщи: существующего покрытия затронутых областей нет, регресс собирать не из чего; предложи скилл test-design. Тест-план не создавай.
```

```markdown
### Шаг 4. Оценка кандидатов

Шаги кейсов читаются ВСЕГДА, но не в главном контексте: раздели кандидатов на пачки по 20–30 ID и запусти суб-агентов (general-purpose, параллельно). Суб-агент SKILL.md не видит — алгоритм передавай явно, в промпт каждого суб-агента подставь выжимку и список ID пачки:

> Ты QA-инженер. Оцени релевантность тест-кейсов Allure TestOps (проект <id>) для регресса по изменению.
>
> Контекст изменения:
> <выжимка ТЗ: Задача + Затронутые области целиком>
>
> Кейсы: <ID пачки через запятую>
>
> Алгоритм по каждому кейсу:
> 1. `get_test_case_overview` — название, поля.
> 2. `get_test_case_scenario` — шаги; пусто → `get_test_case_steps`.
> 3. У шага есть `sharedStepId` → содержимое шага бери через `get_shared_step_steps`.
> 4. У шага нет ожидаемого результата → используй `expectedResult` из overview (общий ОР сценария).
> 5. Вердикт:
>    - ВЗЯТЬ — кейс проверяет функциональность, которую изменение задевает прямо или через общий поток данных;
>    - НЕ БРАТЬ — кейс про другую область, изменение его не касается;
>    - СПОРНО — по шагам связь с изменением однозначно не определяется.
>

>

> | ID | Вердикт | Причина (одна строка, конкретно: какая функция/поток задеты) |

Кандидатов из fallback-поиска по названиям (шаг 3.3) суб-агент оценивает так же, но вердикт ВЗЯТЬ для них понижай до СПОРНО, если причина не указывает на прямое пересечение с изменением.

Собери вердикты всех пачек в один список.
```

```markdown
### Шаг 5. Таблица и подтверждение

Покажи пользователю таблицу (кейсы с вердиктом ВЗЯТЬ, затем блок СПОРНО отдельно; НЕ БРАТЬ в таблицу не включай, дай числом «отсеяно N»):

### Шаг 6. Тест-план

После подтверждения: `create_test_plan` с payload
`{"name": "Регресс: <тема задачи> (redmine-<id задачи>)", "projectId": <proj>, "rql": "id in [<подтверждённые ID через запятую>]"}`.
Если сервер отверг `in` — повтори с `rql` вида `id = <a> or id = <b> or ...`.

Отчитайся: ссылка на тест-план `https://astbroker.qatools.cloud/project/<proj>/test-plans/<id>` (id из ответа), количество кейсов, сколько отсеяно и сколько спорных решено вручную.

## Краевые случаи

- ТЗ не найдено нигде → стоп, вопрос пользователю (шаг 1).
- Секции не сматчились → fallback по названиям, кандидаты спорные (шаг 3).
- Кандидатов > 150 → сузить с пользователем до оценки (шаг 3).
- Релевантных кейсов нет → честно сказать, предложить test-design, план не создавать (шаг 3/5).
- `create_test_plan` запрещён deny-масками (read-only режим Allure) → сообщи об этом и выдай подтверждённый список текстом — это валидный результат.
```
