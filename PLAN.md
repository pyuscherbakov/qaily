# Qaily — план работ

QA AI-ассистент для команды на базе Claude Code: плагин с субагентами, скиллами и MCP-интеграциями (Redmine, Allure TestOps, Kaiten).

**Принятые решения:**
- Тест-менеджмент — Allure TestOps (готовый MCP-сервер)
- Скоуп первой версии — только тест-дизайн (кейсы, планы, регрессия), без генерации автотестов
- Права записи — полные, с индивидуальным read-only переключателем на каждый сервис через permissions
- Доступ к модели — подписки Claude (Pro/Max/Team), своей инфраструктуры нет
- Оркестрация — нативные субагенты Claude Code, без внешних фреймворков

**Критерий выхода:** из чистой сессии Claude Code читается задача Redmine, карточка Kaiten, кейс Allure; создаётся кейс в тестовом проекте Allure; deny-правила блокируют запись.

**Риски:**
- Версия Allure TestOps на сервере несовместима с MCP по API — проверить в первый день фазы.
- Self-hosted Redmine за VPN/прокси — `mcp-redmine` поддерживает `REDMINE_HEADERS` (кастомные заголовки) и `REDMINE_DANGEROUSLY_ACCEPT_INVALID_CERTS=1` (самоподписанный TLS); выяснить у админов заранее.

## Фаза 3 — Субагенты (2 дня)

Цель: пять специализированных агентов с ограниченными инструментами.

| # | Агент | Инструменты | Задача агента |
|---|-------|-------------|---------------|
| 3.1 | `task-analyzer` | Redmine MCP (read) | Из задачи и связанных задач извлечь: функциональные требования, затронутые модули, критерии приёмки, неоднозначности (список вопросов) |
| 3.2 | `doc-researcher` | Kaiten MCP (read) | По ключевым словам из задачи найти релевантные карточки документации, выжать контекст: как фича должна работать, смежные фичи |
| 3.3 | `case-designer` | без MCP | Из брифа (требования + контекст + тип покрытия) сгенерировать кейсы по шаблону команды. Параметризуется типом: позитивные / негативные / граничные |
| 3.4 | `case-reviewer` | Allure MCP (read) | Проверить сгенерированные кейсы: покрытие требований (матрица требование→кейс), дубли с существующими кейсами в Allure, соответствие шаблону |
| 3.5 | `regression-picker` | Redmine + Allure MCP (read) | По списку задач релиза подобрать существующие кейсы Allure для регрессии, разметить приоритеты |

Каждый агент: markdown-файл в `agents/` с frontmatter (name, description, tools) + системный промпт с форматом выхода (структурированный, чтобы оркестратор парсил без догадок).

**Критерий выхода:** каждый агент запускается через Agent tool изолированно и возвращает результат в заявленном формате на 3 реальных задачах из тестового Redmine.

**Принцип:** субагентам write-инструменты не выдаются — вся запись во внешние системы только из главной сессии после подтверждения пользователем.

## Фаза 4 — Скиллы ядра (3–4 дня)

Цель: два главных пайплайна, дающие основную ценность.

### 4.1 `/analyze-task <redmine-id>` (1 день)

Пайплайн: параллельно task-analyzer + doc-researcher → сводка: требования, контекст из документации, чеклист для тестирования, список неоднозначностей для уточнения у аналитика.

Выход — markdown в чате + опционально файл. Записи во внешние системы нет.

### 4.2 `/gen-cases <redmine-id>` (2–3 дня)

Пайплайн:
1. Параллельно: task-analyzer + doc-researcher
2. Оркестратор собирает бриф
3. Параллельно: 3 × case-designer (позитивные / негативные / граничные)
4. case-reviewer: матрица покрытия, дубли, формат
5. Показ пользователю: кейсы + матрица + найденные дубли
6. После подтверждения — создание кейсов в Allure (create_test_case + теги + связь с задачей через issue links)

Дополнительно:
- Флаг `--dry-run` — только показать, ничего не заливать
- Обработка отказа: пользователь правит кейсы текстом, оркестратор перегенерирует точечно

**Критерий выхода:** на 5 реальных задачах разного типа (новая фича, багфикс, изменение существующего) `/gen-cases` даёт кейсы, которые QA-лид оценивает как «готовы или требуют минимальной правки» минимум в 3 из 5 случаев. Кейсы корректно появляются в Allure с тегами и связями.

**Риск:** качество генерации упирается в качество описаний задач в Redmine. Если описания скудные — ценность смещается в `/analyze-task` (список вопросов аналитику). Замерить на пилоте.

## Ключевые риски

1. **Скудные описания задач в Redmine** — главный риск качества. Митигация: `/analyze-task` генерирует вопросы аналитику; замер на пилоте.
2. **Несовместимость версий API** (Allure TestOps, Redmine) с готовыми MCP — проверять в первый день фазы 2, запас на свой Redmine MCP заложен.
3. **Шаблоны и соглашения команды не формализованы** — без них generic-кейсы. Митигация: встреча с QA-лидом в фазе 1, итерации в пилоте.
4. **Лимиты подписок** при параллельных субагентах (3 designer + reviewer за прогон). Митигация: замерить расход на пилоте; при упоре в лимиты — снизить параллелизм до 1 designer с тремя секциями.
