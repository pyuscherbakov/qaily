## Платформа и проект

Сначала определи фактический клиент и доступные инструменты. Разреши реальный абсолютный путь этого SKILL.md через все символьные ссылки к установленной копии пакета; относительные пути ниже разрешай от каталога этого реального файла, не от cwd и не от каталога неразрешённой ссылки. Прочитай соответствующий адаптер `../../references/platforms/claude.md` или `../../references/platforms/codex.md` и общие правила `../../references/project-selection.md` до обращения к TestOps. Неизвестный клиент сообщи как ограничение. Выбранный эффективный `projectId` передавай каждому субагенту вместе с абсолютным `procedure_path` соответствующего файла в `../../references/agents/`.


# Ревью автотеста

Ты ведёшь ревью автотестов: определяешь объём работы, собираешь входные данные и раздаёшь кейсы суб-агенту `autotest-reviewer`, который ревьюит по одному кейсу. Твоя зона — режимы, сбор данных и сводка. Сам алгоритм ревью одного кейса, блоки проверок и правила формулировок живут в `../../references/agents/autotest-reviewer.md`; агент читает их сам — **не пересказывай их в промпте агента**.

Скилл запускается из cwd репозитория автотестов. Связка кейс ↔ код — через декоратор `@allure.id("<id>")` в коде теста или, в параметризованных тестах, вызов `allure.dynamic.id(...)` в теле (id — литерал или значение из `parametrize`). Дальше «`@allure.id`» — любая из двух форм.

## Режимы (по входу пользователя)

Определи режим по тому, что дал пользователь:

- **Redmine-задача** (`#1234`, `redmine.fast-system.ru/issues/1234`) → **пачечный режим**: ревью всех связанных с задачей кейсов TestOps.
- **TestOps-кейс** (число, ссылка `.../test-cases/<id>`) → **одиночный режим**: один кейс + его автотест.
- **GitLab MR** (ссылка на merge request) → **diff-режим**: ревью только изменённых в MR тест-файлов.

Если вход неоднозначен — уточни у пользователя, что ревьюим.

`projectId` TestOps: выбери по общим правилам project-selection до вызова TestOps; голый ID использует default 1, ссылка `/project/37/test-cases/<id>` использует 37. Конфликт явного проекта со ссылкой уточни до TestOps. В MR-режиме сначала определи, есть ли изменённые тест-файлы: если нет, проект не нужен и вопрос о нём не задавай.

## Критические правила

1. **Ревью read-only.** Ничего в коде, кейсах и Redmine-задачах не изменяй — только читай и анализируй. Не вызывай обновление статуса, поля «Назначен» или другие операции записи. Конкретные правки предлагаются в ответе, не применяются.
2. **Делегирование обязательно.** Каждый кейс ревьюит суб-агент по процедуре `autotest-reviewer.md` (доступным изолированным делегированием из адаптера) — так код автотестов не читается inline в главный тред, а алгоритм ревью остаётся в одном месте. В Codex, если вызов требует `agent_name`, используй допустимое имя `autotest_reviewer` (имя файла с дефисом не является допустимым `agent_name`); Claude wrapper сохраняет своё имя `autotest-reviewer`.
3. **Вход агенту — только данные:** `case_id` (или `file` + `tests` — для тестов без `@allure.id`), `projectId` (вместе с `case_id` — всегда), `cwd` репы автотестов, выжимка требований задачи (если уже достал) и нужный формат ответа. Шаги алгоритма, блоки проверок и правила формулировок не дублируй.
4. **Требования Redmine тяни один раз** — в пачечном и MR-режиме, на уровне режима, и передавай агентам, иначе каждый агент дёрнет Redmine заново. В одиночном режиме Redmine сам не дёргай: агент найдёт ссылку в полях кейса.

## Одиночный режим

Один изолированный вызов по `autotest-reviewer.md`: `case_id`, `projectId`, `cwd`, формат `полный`. Требования агент достанет сам по ссылкам кейса. Родитель до делегирования не читает кейс, общий шаг, Redmine и код: это работа агента. Если делегирование невозможно, сообщи ограничение и остановись без inline-ревью.

Вывод агента отдай пользователю как есть.

## Пачечный режим (Redmine-задача)

1. `redmine_request`, GET `issues/<id>.json` с `params: {include: "attachments,journals"}` → задача. Требования = описание + комментарии + вложения (ТЗ часто лежит во вложениях; как читать — раздел «Вложения Redmine» в файле агента `../../references/agents/autotest-reviewer.md` относительно базового каталога этого скилла — Read его перед сбором требований). Неразобранные вложения перечисли в выжимке — агент вынесет их в «Не проверено».
2. **Кейсы задачи** — `testops_find_testcases` с `projectId` и `aql: "tag = \"redmine-<id>\""` (кейсы, созданные тест-дизайном по задаче). Кейсы, привязанные к задаче только полем «Связанные задачи», этот поиск не находит — в шапке сводки строка «найдены только кейсы с тегом redmine-<id>». Ошибка, усечение или некорректный формат **списка** → краевой случай «ошибка API на сборе данных», остановка без частичной таблицы; пустой корректный список → «нет связанных кейсов».
3. На каждый кейс — свой `autotest-reviewer`: `case_id`, `projectId`, выжимка требований, `cwd`, формат `сжатый`.
4. Проверь ответы агентов и собери сводную таблицу из строк статуса; подшей детали по кейсам с замечаниями и по частично проверенным (для них — строки «Не проверено: …»). Сбой отдельного кейса или агента не прекращает остальные вызовы.

## MR-режим (GitLab merge request, diff-центричный)

1. **Достать изменённые тест-файлы** доступным read-only механизмом из адаптера:
   - если ветка MR есть локально → `git diff --name-only <base>...<branch>` (base по умолчанию `main`/`master` — определи по репе) → отфильтруй тест-файлы (`test_*.py` / `*_test.py`);
   - иначе → GitLab API по URL MR через `curl` (`GET /projects/:id/merge_requests/:iid/changes`, заголовок `PRIVATE-TOKEN: $GITLAB_TOKEN`) или `glab mr diff`, если установлен. Токен не задан → сообщи, что для удалённого MR нужен GitLab-токен, предложи вариант с локальной веткой.
   Ошибка получения diff/списка файлов — остановка; не принимай её за пустой MR. Если корректный список не содержит тест-файлов, ответь «в MR нет автотестов» и остановись до выбора `projectId`.
2. **Требования:** из описания MR извлеки номер Redmine-задачи → требования так же, как в шаге 1 пачечного режима (с вложениями, один раз). Если номера задачи нет, передай агентам явную пометку «требования недоступны: в MR нет ссылки на задачу», чтобы блок 2 был отмечен как непроверенный без повторных запросов.
3. **Кейсы — по тестам, не по файлам.** В каждом изменённом тест-файле пройди по тест-функциям и раздели их на две группы: с привязкой `@allure.id` (декоратор или `allure.dynamic.id` в теле, id параметризованного теста бери из `parametrize`) и без неё. Файл попадает в обе группы сразу, если содержит и те и другие — типичный случай, когда в существующий файл добавили новый тест.
4. **Ревью** (формат `сжатый`, требования или пометка об их недоступности переданы как данные):
   - на каждый найденный `case_id` — `autotest-reviewer` с `case_id` и `projectId`;
   - на каждый файл с тестами без `@allure.id` — `autotest-reviewer` с `file` и списком `tests` (имена функций без привязки): режим «без кейса», код ревьюится, отсутствие привязки к TestOps попадает в замечания.
5. **Вывод:** сводка + детали.

MR без изменённых тест-файлов → сообщи «в MR нет автотестов», останови.

Перед добавлением строки в сводку проверь, что ответ агента завершён, первая строка имеет ровно четыре поля и ожидаемый `case_id` (или `—` для режима без кейса), статус входит в контракт `autotest-reviewer`, а число замечаний согласуется с деталями. `Готов` с любой строкой «Не проверено» или непроверенным обязательным блоком недопустим. Усечённый, ошибочный или противоречивый ответ отрази отдельной строкой `⚠ ревью не завершено` с причиной и числом `—`; не превращай его в «Готов» и продолжай остальные кейсы. Не передавай агенту процедуру текстом в spawn prompt: только абсолютный `procedure_path`, эффективный `projectId`, необходимые входные данные и просьбу самостоятельно прочитать процедуру. Для каждого `case_id` — отдельный изолированный вызов; нехватку слотов обработай очередью без потери кейсов.

## Формат сводки (пачка / MR)

```
Ревью: задача #1234 — 5 кейсов

| Кейс  | Тест           | Статус          | Замечаний |
|-------|----------------|-----------------|-----------|
| 39979 | test_calc_gap  | Нужна доработка | 2         |
| 39980 | test_calc_base | Готов           | 0         |
| 39981 | — (не найден)  | ⚠ нет автотеста | 1         |
| 39982 | test_calc_docs | ⚠ проверено частично | 0    |
| —     | test_calc_new  | Нужна доработка | 3         |

Детали ниже — только по кейсам с замечаниями и по частично проверенным.
```

Все кейсы со статусом «Готов» → таблица плюс одна строка: «Автотесты соответствуют кейсам и требованиям, правки не требуются».

## Краевые случаи

- **Redmine / TestOps / GitLab API ошибка на сборе списка** → сообщить пользователю, остановить (по частичному списку кейсов не ревьюить). Сбой отдельного вложения — не стоп: имя в «не разобраны вложения» выжимки, ревью идёт дальше.
- **У задачи нет связанных кейсов TestOps** → сообщить «к задаче не привязаны кейсы», остановить.
- **MR без изменённых тест-файлов** → «в MR нет автотестов», стоп.
- **Тест без `@allure.id`** → не пропускать, даже если в том же файле есть тесты с привязкой: агент в режиме «без кейса», в таблице строка с `—` в колонке кейса.
- **Агент вернул «⚠ кейс недоступен»** → строка в таблице остаётся, остальные кейсы ревьюятся дальше.
