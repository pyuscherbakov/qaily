# Ревью автотеста

Ты ведёшь ревью автотестов: определяешь объём работы, собираешь входные данные и раздаёшь кейсы суб-агенту `autotest-reviewer`, который ревьюит по одному кейсу. Твоя зона — режимы, сбор данных и сводка. Сам алгоритм ревью одного кейса, блоки проверок и правила формулировок живут в `agents/autotest-reviewer.md`; агент читает их сам — **не пересказывай их в промпте агента**.

Скилл запускается из cwd репозитория автотестов. Связка кейс ↔ код — через декоратор `@allure.id("<id>")` в коде теста или, в параметризованных тестах, вызов `allure.dynamic.id(...)` в теле (id — литерал или значение из `parametrize`). Дальше «`@allure.id`» — любая из двух форм.

## Режимы (по входу пользователя)

Определи режим по тому, что дал пользователь:

- **Redmine-задача** (`#1234`, `redmine.fast-system.ru/issues/1234`) → **пачечный режим**: ревью всех связанных с задачей кейсов TestOps.
- **TestOps-кейс** (число, ссылка `.../test-cases/<id>`) → **одиночный режим**: один кейс + его автотест.
- **GitLab MR** (ссылка на merge request) → **diff-режим**: ревью только изменённых в MR тест-файлов.

Если вход неоднозначен — уточни у пользователя, что ревьюим.

## Критические правила

1. **Ревью read-only.** Ничего в коде, кейсах и Redmine-задачах не изменяй — только читай и анализируй. Конкретные правки предлагаются в ответе, не применяются.
2. **Делегирование обязательно.** Каждый кейс ревьюит суб-агент `autotest-reviewer` (Agent tool) — так код автотестов не читается inline в главный тред, а алгоритм ревью остаётся в одном месте.
3. **Вход агенту — только данные:** `case_id` (или `file` + `tests` — для тестов без `@allure.id`), `projectId` (по умолчанию 35), `cwd` репы автотестов, выжимка требований задачи (если уже достал) и нужный формат ответа. Шаги алгоритма, блоки проверок и правила формулировок не дублируй.
4. **Требования Redmine тяни один раз** — в пачечном и MR-режиме, на уровне режима, и передавай агентам, иначе каждый агент дёрнет Redmine заново. В одиночном режиме Redmine сам не дёргай: агент найдёт ссылку в полях кейса.

## Одиночный режим

Один вызов `autotest-reviewer`: `case_id`, `cwd`, формат `полный`. Требования агент достанет сам по ссылкам кейса.

Вывод агента отдай пользователю как есть.

## Пачечный режим (Redmine-задача)

1. `redmine_request`, GET `issues/<id>.json` с `params: {include: "attachments,journals"}` → задача и список связанных TestOps-кейсов. Требования = описание + комментарии + вложения (ТЗ часто лежит во вложениях; как читать — раздел «Вложения Redmine» в файле агента `../../agents/autotest-reviewer.md` относительно базового каталога этого скилла — Read его перед сбором требований). Неразобранные вложения перечисли в выжимке — агент вынесет их в «Не проверено».
2. На каждый кейс — свой `autotest-reviewer`: `case_id`, выжимка требований, `cwd`, формат `сжатый`.
3. Собери сводную таблицу из строк статуса и подшей детали по кейсам с замечаниями и по частично проверенным (для них — строки «Не проверено: …»).

## MR-режим (GitLab merge request, diff-центричный)

1. **Достать изменённые тест-файлы:**
   - если ветка MR есть локально → `git diff --name-only <base>...<branch>` (base по умолчанию `main`/`master` — определи по репе) → отфильтруй тест-файлы (`test_*.py` / `*_test.py`);
   - иначе → GitLab API по URL MR через `curl` (`GET /projects/:id/merge_requests/:iid/changes`, заголовок `PRIVATE-TOKEN: $GITLAB_TOKEN`) или `glab mr diff`, если установлен. Токен не задан → сообщи, что для удалённого MR нужен GitLab-токен, предложи вариант с локальной веткой.
2. **Требования:** из описания MR извлеки номер Redmine-задачи → требования так же, как в шаге 1 пачечного режима (с вложениями, один раз).
3. **Кейсы — по тестам, не по файлам.** В каждом изменённом тест-файле пройди по тест-функциям и раздели их на две группы: с привязкой `@allure.id` (декоратор или `allure.dynamic.id` в теле, id параметризованного теста бери из `parametrize`) и без неё. Файл попадает в обе группы сразу, если содержит и те и другие — типичный случай, когда в существующий файл добавили новый тест.
4. **Ревью** (формат `сжатый`, требования переданы):
   - на каждый найденный `case_id` — `autotest-reviewer` с `case_id`;
   - на каждый файл с тестами без `@allure.id` — `autotest-reviewer` с `file` и списком `tests` (имена функций без привязки): режим «без кейса», код ревьюится, отсутствие привязки к TestOps попадает в замечания.
5. **Вывод:** сводка + детали.

MR без изменённых тест-файлов → сообщи «в MR нет автотестов», останови.

## Формат сводки (пачка / MR)

```
Ревью: задача #1234 — 5 кейсов

| Кейс  | Тест           | Статус          | Замечаний |
|-------|----------------|-----------------|-----------|
| 39979 | test_calc_gap  | Нужна доработка | 2         |
| 39980 | test_calc_base | Готов           | 0         |
| 39981 | — (не найден)  | ⚠ нет автотеста | 1         |
| 39982 | test_calc_docs | ⚠ проверено частично | 0    |
| —     | test_calc_new  | Нужна доработка | 3         |

Детали ниже — только по кейсам с замечаниями и по частично проверенным.
```

Все кейсы со статусом «Готов» → таблица плюс одна строка: «Автотесты соответствуют кейсам и требованиям, правки не требуются».

## Краевые случаи

- **Redmine / GitLab API ошибка на сборе данных** → сообщить пользователю, остановить (по частичному списку кейсов не ревьюить). Сбой отдельного вложения — не стоп: имя в «не разобраны вложения» выжимки, ревью идёт дальше.
- **У задачи нет связанных кейсов TestOps** → сообщить «к задаче не привязаны кейсы», остановить.
- **MR без изменённых тест-файлов** → «в MR нет автотестов», стоп.
- **Тест без `@allure.id`** → не пропускать, даже если в том же файле есть тесты с привязкой: агент в режиме «без кейса», в таблице строка с `—` в колонке кейса.
- **Агент вернул «⚠ кейс недоступен»** → строка в таблице остаётся, остальные кейсы ревьюятся дальше.
