# Тест-дизайн: генерация кейсов по требованию

## Входные данные

Определи источник требования из запроса пользователя:
- Номер задачи Redmine («задача №123») → прочитай через `redmine_request` (GET `issues/123.json`, `params: {include: "attachments,journals"}`).
- Карточка Kaiten («карточка 456») → прочитай через `kaiten_get_card`.
- Документ/wiki Kaiten («документ такой-то», ссылка на документ) → найди через `kaiten_list_documents` (query), прочитай через `kaiten_get_document`.
- Текст требования прямо в запросе → используй как есть.

Целевой проект Allure: по умолчанию 35 (тестовый). Другой проект — только если пользователь указал явно.

## Процесс

1. **Собери контекст субагентом**: делегируй чтение требования и поиск покрытия субагенту `doc-researcher` (read-only, изолированный контекст) — передай источник (задача Redmine / карточка Kaiten / текст) и целевой проект. Он вернёт выжимку: строки «Не проверено» (недоступные источники, неразобранные вложения), суть требования, полный список критериев и правил с точными значениями, неоднозначности, существующее покрытие, пробелы, источники. Классы эквивалентности и границы строй по «Критериям и правилам». Для простого текстового требования без интеграций субагента можно пропустить и разобрать инлайн.
2. **Проверь выжимку с пользователем**: неоднозначности и строки «Не проверено» из отчёта перечисли пользователю ДО генерации — не выдумывай поведение системы; неразобранное вложение могло содержать ТЗ — спроси, есть ли его текст. Найденные кейсы покажи — дубли не создавай. «Не проверено: покрытие TestOps» — предупреди, что дубли не исключены.
3. **Спроектируй кейсы** техниками тест-дизайна (на основе пробелов из выжимки):
   - классы эквивалентности и граничные значения для входных данных;
   - позитивные И негативные сценарии (невалидный ввод, отказ смежной системы, права доступа);
   - состояния и переходы, если требование описывает workflow.
4. **Покажи пользователю таблицу кейсов** (название, приоритет, шаги кратко) и дождись подтверждения перед записью в Allure.
5. **После подтверждения** создай кейсы через `testops_create_testcase` (`projectId`, `name`, `scenario`, `tags`): название по шаблону «<Фича>. <Сценарий>», шаги как scenario, ожидаемый результат в каждом шаге. Источник — задача Redmine → обязательно `tags: ["redmine-<id>"]` ровно в этом формате: по нему `doc-researcher` находит прямое покрытие при повторном тест-дизайне. Источник — Kaiten или текст → тег не ставь.
6. **Отчитайся**: список созданных кейсов со ссылками вида `https://astbroker.qatools.cloud/project/35/test-cases/<id>`.

## Ограничения

- Без подтверждения пользователя ничего в Allure не создавать.
- В Redmine и Kaiten — только чтение, никаких изменений.
- Запись в TestOps требует подтверждения пользователя на каждый вызов (ask-правила). Отказ в подтверждении — выдай кейсы текстом, не пытайся обойти.
