# Тест-дизайн: генерация кейсов по требованию

## Входные данные

Определи источник требования из запроса пользователя — сам его не читай, это делает `doc-researcher` (шаг 1):
- номер задачи Redmine («задача №123»);
- карточка Kaiten («карточка 456»);
- документ Kaiten («документ такой-то», ссылка на документ);
- текст требования прямо в запросе.

Целевой проект Allure выбирай по общим правилам project-selection; default — 1.

## Процесс

1. **Собери контекст субагентом**: делегируй чтение требования и поиск покрытия субагенту `doc-researcher` (read-only, изолированный контекст) — передай источник (задача Redmine / карточка Kaiten / документ Kaiten / текст) и целевой проект. Он вернёт выжимку: строки «Не проверено» (недоступные источники, неразобранные вложения), суть требования, полный список критериев и правил с точными значениями, неоднозначности, существующее покрытие, пробелы, источники. Классы эквивалентности и границы строй по «Критериям и правилам». Для простого текстового требования без интеграций субагента можно пропустить и разобрать инлайн.
2. **Проверь выжимку с пользователем**: неоднозначности и строки «Не проверено» из отчёта перечисли пользователю ДО генерации — не выдумывай поведение системы; неразобранное вложение могло содержать ТЗ — спроси, есть ли его текст. Найденные кейсы покажи — дубли не создавай. «Не проверено: покрытие TestOps» — предупреди, что дубли не исключены. Выжимка состоит только из строк «Не проверено» (требование не прочитано) → попроси у пользователя текст требования и дальше не иди: проектировать не из чего.
3. **Спроектируй кейсы** техниками тест-дизайна (на основе пробелов из выжимки):
   - классы эквивалентности и граничные значения для входных данных;
   - позитивные И негативные сценарии (невалидный ввод, отказ смежной системы, права доступа);
   - состояния и переходы, если требование описывает workflow.
4. **Покажи пользователю таблицу кейсов** (название, приоритет, шаги кратко) и дождись подтверждения перед записью в Allure.
5. **После подтверждения** создай кейсы через `testops_create_testcase` (`projectId`, `name`, `scenario`, `tags`): название по шаблону «<Фича>. <Сценарий>», шаги как scenario, ожидаемый результат в каждом шаге. Источник — задача Redmine → обязательно `tags: ["redmine-<id>"]` ровно в этом формате: по нему `doc-researcher` находит прямое покрытие при повторном тест-дизайне. Источник — Kaiten или текст → тег не ставь.
6. **Отчитайся**: список созданных кейсов со ссылками вида `<effective-url>/project/<projectId>/test-cases/<id>`.

## Ограничения

- Без подтверждения пользователя ничего в Allure не создавать.
- В Redmine и Kaiten — только чтение, никаких изменений.
- Запись в TestOps требует подтверждения пользователя на каждый вызов (ask-правила). Отказ в подтверждении — выдай кейсы текстом, не пытайся обойти.
