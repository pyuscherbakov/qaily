# Coverage-gap-design: тест-дизайн от пробелов покрытия

Идея (по статье ВкусВилл про swagger-coverage): контракт API — источник задач для тест-дизайна.
Не проектируем вслепую — сначала считаем, что уже покрыто, потом закрываем дыры.

## Входные данные

Источник контракта (обязателен):
- Путь к OpenAPI/Swagger файлу (`.yaml`/`.json`) → прочитай через `Read`.
- URL спеки → прочитай через `WebFetch` (спрашивай отдать paths+operations+responses как есть).

Отчёт покрытия (опционален, но это главный сигнал):
- Путь к JSON-отчёту `swagger-coverage` → `Read`. Из него берётся статус операций: full / partial / empty, и по каким условиям (status-коды, параметры, тело, свойства ответа) нет вызовов.
- Нет отчёта → покрытие оцениваем только по существующим кейсам Allure (см. ниже).

Целевой проект Allure: по умолчанию 35 (тестовый). Другой — только если пользователь указал явно.

## Процесс

1. **Разбери контракт**: из спеки собери список операций `<METHOD> <path>` с их `operationId`, параметрами, телом запроса, объявленными статус-кодами и схемой ответа.
2. **Определи покрытие каждой операции** — из двух источников:
   - swagger-coverage JSON (если дан): статус full/partial/empty + непокрытые условия.
   - Allure: `search_test_cases` в целевом проекте по `operationId` и по тегам вида `api-<method>-<path>` (см. шаг 6). Пара ближайших кейсов — `get_test_case_scenario`, чтобы понять глубину.
3. **Составь список пробелов** и покажи пользователю таблицей ДО генерации:
   - непокрытые операции (empty);
   - частично покрытые (partial) — какие статус-коды / параметры / свойства ответа без кейса;
   - неоднозначности контракта (нет описания ошибок, размытые схемы) — перечисли, не выдумывай поведение.
   Полностью покрытые (full) — пропускаем, дубли не создаём.
4. **Спроектируй кейсы ТОЛЬКО на пробелы** техниками тест-дизайна:
   - на каждый объявленный, но непокрытый статус-код — отдельный сценарий (200/201, 400 невалидный ввод, 401/403 права, 404, 409/422 бизнес-конфликт);
   - классы эквивалентности и границы для непокрытых параметров/полей тела;
   - обязательные vs опциональные параметры, нарушение типов/форматов;
   - проверка ключевых свойств ответа (схема, обязательные поля).
5. **Покажи таблицу кейсов** (название, приоритет, шаги кратко) и дождись подтверждения перед записью в Allure.
6. **После подтверждения** создай кейсы через `create_test_case`:
   - название: «<Ресурс/operationId>. <METHOD path> — <сценарий>»;
   - шаги как scenario, ожидаемый результат в каждом шаге (в т.ч. ожидаемый статус-код и ключевые поля ответа);
   - теги: `api-<method>-<path-без-параметров>` (напр. `api-post-cohorts`) + `operationId`, если есть. По этим тегам следующий прогон увидит покрытие.
7. **Отчитайся**: список созданных кейсов со ссылками `https://astbroker.qatools.cloud/project/35/test-cases/<id>` и остаток непокрытых операций (что осталось на ручной бизнес-тест-дизайн).

## Ограничения

- Без подтверждения пользователя ничего в Allure не создавать.
- Спека и coverage-отчёт — только чтение.
- Контракт покрывает технический слой, НЕ бизнес-сценарии — сложные сценарии оставляй на скилл `test-design` (источник Redmine/Kaiten). В отчёте так и помечай.
- Если `create_test_case` запрещён deny-масками — сообщи про read-only и выдай кейсы текстом.
