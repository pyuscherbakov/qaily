# Разбор упавшего прогона

Ты разбираешь упавший запуск Allure TestOps: берёшь статистику, находишь задачу запуска, раздаёшь чтение результатов суб-агенту `failure-analyst` и сводишь всё в одну сводку. Алгоритм чтения одного результата, правила нормализации сигнатур и типы причин живут в `agents/failure-analyst.md` — агент читает их сам, **не пересказывай их в промпте агента**.

## Вход

- Число (`4498`) или ссылка `https://astbroker.qatools.cloud/launch/<id>` → id запуска.
- `projectId` — по умолчанию <дефолт из Task 4>. Пользователь может задать явно.

## Критические правила

1. **Read-only.** Ни кейсы, ни дефекты, ни задачи не создаём и не меняем. Файлы не пишем — сводка идёт в чат.
2. **Делегирование обязательно.** Результаты прогона приходят вместе с `trace`; читать их в главном треде нельзя — контекст взорвётся. Любое чтение результатов и задачи — через `failure-analyst`.
3. **Задачу тянем один раз** — режимом `context`, и передаём выжимку всем `drill`-вызовам. Агенты Redmine сами не дёргают.
4. **Лимиты:** до 8 агентов `scan` параллельно, до 12 агентов `drill` на прогон.

## Шаг 1. Статистика запуска

`testops_find_launches`:

````
projectId: <projectId>
aql: "id = <launch>"
expand: ["statistic","issues","release","category","defect","unresolved","uncategorized"]
````

Из ответа возьми: имя запуска, `release`, `issues`, `statistic` (по статусам), и сколько падений TestOps уже разложил по дефектам (`defect` / `uncategorized`).

- Пустой результат (`totalElements: 0`) → запуск в другом проекте: спроси у пользователя `projectId`, не перебирай проекты сам.
- `failed` + `broken` = 0 → ответь «прогон зелёный, падений нет» и остановись.

## Шаг 2. Номер Redmine-задачи

Порядок источников:
1. `issues[0]` — MCP отдаёт массивом строк (`["43203"]`). Строка из одних цифр → это номер задачи Redmine.
2. Иначе `release` — имя релиза часто и есть номер задачи (`"43203"`).
3. Ни то ни другое (или значение не число) → работаем без контекста, в сводке строка «задача не определена, анализ только по ошибкам».

## Шаг 3. Раздача агентов

Параллельно, одним блоком вызовов:
- один `failure-analyst` с `mode: context`, `issue_id` — если номер нашёлся;
- `failure-analyst` с `mode: scan` на каждую страницу: страниц = ceil((failed + broken) / 50), но не больше 8 за раз; вход каждому: `projectId`, `launch`, `page`, `size: 50`.

Падений больше 400 → бери первые 8 страниц и отметь в сводке, сколько результатов осталось непросмотренными.

## Шаг 4. Мерж групп

Сложи строки `SIG:` из всех `scan`-ответов: одинаковая сигнатура из разных страниц — одна группа, счётчики складываются, представителей берём до 3 (по одному с разных страниц, если возможно).

Отсортируй по убыванию количества. Группы с 1 падением и непохожими сигнатурами сложи в один блок «прочее» — на них `drill` не тратим, если групп и так 12.

## Шаг 5. Разбор групп

На каждую группу (максимум 12, начиная с самых крупных) — `failure-analyst` с `mode: drill`, входом `projectId`, `signature`, `count`, `result_ids`, `issue_context` (выжимка из шага 3; нет задачи — пустая строка). Подгруппы в сводке идут отдельными строками таблицы с общим номером группы (`3a`, `3b`).

## Формат сводки

```
Launch 5034 «Запуск от 18/09/2026 18:13» · релиз 43203 · Redmine #43203 — <тема задачи>
773 теста: 477 passed, 56 failed, 240 broken, 8 skipped
TestOps уже разложил по дефектам: 12 падений (осталось разобрать 284)

| # | Тип                    | Причина                                   | Падений | Примеры |
|---|------------------------|-------------------------------------------|---------|---------|
| 1 | инфра/авторизация      | 401 на справочниках при старте теста       | 240     | 39979   |
| 2 | продуктовый дефект     | HTTP 500 на /contracts/calculate (ВСК)     | 12      | 40012   |
| 3 | тестовые данные        | ВЕСТА GFK350 не привязана к СК             | 9       | 40031   |

Детали по группам — причина, где ломается, что чинить.

### 1. 401 на справочниках — инфра/авторизация
Причина: ...
Где: ...
Что чинить: ...
```

Хвостом сводки — блок «Что дальше»: для устойчивых групп предложи закрепить их дефектом TestOps (`testops_create_defect` с `matcher.messageRegex`), чтобы следующий прогон раскладывался автоматически. **Предлагай, не выполняй.**

## Краевые случаи

- **Запуск не найден** → спросить `projectId`, не перебирать проекты.
- **Падений нет** → «прогон зелёный», стоп.
- **Redmine недоступен** (агент `context` вернул «Задача недоступна») → разбор продолжаем без контекста, в шапке сводки строка «контекст задачи недоступен: <причина>».
- **Агент `scan` упал на своей странице** → остальные страницы идут дальше; в сводке строка «страница N не прочитана, результаты не учтены».
- **Все падения уже разложены дефектами TestOps** → сводка из одной таблицы известных дефектов, `drill` не запускаем.
